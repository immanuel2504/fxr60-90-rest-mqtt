DELETE /cloud/logs/syslog - purge the system log
RESULT: HTTP 200, empty body - and CONFIRMED by size comparison

  before DELETE:  GET /cloud/logs/syslog -> 200, 33392 bytes
  DELETE:         200, empty body
  after DELETE:   GET /cloud/logs/syslog -> 200,   396 bytes

Decoding the after-archive confirms a real purge rather than a truncated
response - the "messages" member went from 72394 bytes to 346, and its only
remaining content is the post-purge restart notice:

  2026-09-05T17:36:56.694029+00:00 FXR609BE34A rsyslogd: [origin
  software="rsyslogd" ...] rsyslogd was HUPed

So the reader truncates the file and signals rsyslogd (SIGHUP) to reopen it,
which is the correct way to rotate a live syslog. The 346 bytes are entries
generated by the purge itself.

IDEMPOTENT: a second DELETE on the already-purged log also returns HTTP 200.

Note the contrast with the sibling endpoint: after purging, syslog still returns
HTTP 200 with a near-empty archive, whereas radioPacketLog returns HTTP 422. See
../cloud-logs-radioPacketLog-GET/02-empty-returns-422/.

NO CONFIRMATION STEP. This is a destructive, irreversible operation with no
dry-run, no "are you sure" parameter and no backup. One unauthenticated-looking
DELETE and the diagnostic history is gone. Auth IS enforced (401 without a
token), which is the only guard. Capture the log with GET first - that is what
was done here, into /tmp/logbase/, before any DELETE was issued.
