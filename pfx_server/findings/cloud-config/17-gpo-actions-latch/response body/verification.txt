CONCLUSIONS

1. CLOUD_CONNECT fires. Pin 1 went LOW -> HIGH from a verified-LOW baseline, and
   /cloud/status shows the AWS data interface connected. This is the first
   confirmation that the two cloud events in GPIO-LED are wired to real firmware
   events, not just accepted by the validator.

2. CLOUD_DISCONNECT also fires in the same operation. Pin 2 went LOW -> HIGH too.
   Applying a new endpoint configuration tears down the existing cloud connection
   before bringing up the new one, so within one PUT the reader emits
   CLOUD_DISCONNECT (old connection dropped) and then CLOUD_CONNECT (new one up).
   Both actions latch their pins HIGH and neither clears the other, so the end
   state has both HIGH while the reader is, in fact, connected.

   This is consistent behaviour, but it means GPO 1 and GPO 2 cannot be read as a
   current-state indicator of cloud connectivity — they are latched event
   counters. To use them as a state indicator, CLOUD_CONNECT must also drive the
   disconnect pin back LOW and vice versa, e.g.

     "CLOUD_CONNECT":    [{"type":"GPO","pin":1,"state":"HIGH"},
                          {"type":"GPO","pin":2,"state":"LOW"}]
     "CLOUD_DISCONNECT": [{"type":"GPO","pin":2,"state":"HIGH"},
                          {"type":"GPO","pin":1,"state":"LOW"}]

   The LED actions do not have this problem: LED 2 is a single resource that the
   two events set to different colours, so the last event wins and the LED does
   show current state.

3. RADIO_START correctly did NOT fire. Pin 3 stayed LOW, matching
   radioActivity: "inactive" — no inventory was started in this test. This is a
   useful negative control: it shows pins 1 and 2 going HIGH was event-driven and
   not a side effect of applying a configuration.

4. TAG_READ did not fire. Pin 4 stayed LOW. Expected — the radio was never
   started, so no tags were read.
