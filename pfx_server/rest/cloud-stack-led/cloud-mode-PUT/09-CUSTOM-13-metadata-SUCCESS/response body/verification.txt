*** THE FIELD NAME MAPPING - requested vs delivered ***

The names you request are NOT the names you receive. Documenting the mapping,
since nothing in the spec states it:

    requested         delivered in the tag event
    ANTENNA        -> antenna
    RSSI           -> peakRssi          (not "rssi")
    PHASE          -> phase
    SEEN_COUNT     -> reads             (not "seenCount")
    CHANNEL        -> channel
    PC             -> PC
    XPC            -> (not present on these tags)
    CRC            -> CRC
    EPC            -> EPC
    TID            -> TID
    USER           -> USER
    MAC            -> MAC
    HOSTNAME       -> hostName          (not "HOSTNAME" or "hostname")

Note the casing is inconsistent in the OUTPUT too: some fields come back
UPPERCASE (PC, CRC, EPC, TID, USER, MAC) and others camelCase (antenna,
peakRssi, channel, phase, reads, hostName). A client has to know both
conventions.

XPC was requested and accepted but does not appear - presumably because these
tags carry no XPC word. Absence is silent.

*** USER MEMORY RETURNS AN ERROR STRING, NOT AN ERROR ***

    "USER": "Error: tag returned error code 0x03 = Memory overrun"

The tags in this field have no USER memory bank. Rather than omitting the field
or signalling a per-tag failure, the reader puts a human-readable error message
in the field where data is expected. A client parsing USER as hex data would get
a 52-character English sentence.

That is worth raising: the value is neither valid data nor absent, and its type
(string) is indistinguishable from a successful read.

The MAC and hostName fields correctly identify the reader itself
(88:BC:AC:9B:E3:4A / FXR609BE34A), which is useful for multi-reader deployments.
